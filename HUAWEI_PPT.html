一、场景背景

智能体正从「能对话」走向「能做事」。一旦 AI 被授予真实支付能力，企业面临的不再是模型能力问题，而是资金安全与责任归因问题。

二、真实痛点（三条）

  • 缺乏事前管控：多数智能体的金额管控在付款之后才生效，钱已出手。
  • 提示词护栏可被绕过：把「不许乱花钱」写进 prompt，模型可被说服放行——护栏缺少架构级保证。
  • 决策无法归因：智能体为什么买这件、为什么放行，事后查不到证据链。
目标用户：需要给 AI 智能体授予受限支付/采购权限的企业与超级个体（OPC）。

三、PayPilot 的应对

  • 在触碰资金之前执行策略引擎（pre-flight），不过闸则不调用支付 API。
  • 策略覆写路径对大模型不可见——不是「提示词里写一句」，而是模型根本拿不到绕过开关。
  • 每一步决策产出带字段引用的审计链，可完整回放。

决策链（7 步，全链路可审计）

PERCEIVE→ SEARCH→ SELECT→ POLICY→ EXPLAIN→ EXECUTE→ CAPTURE

POLICY 是关键闸口：位于 EXECUTE 之前，未通过则不进入支付调用。策略判定独立于模型输出，模型只能看到「通过/拒绝」的结果，看不到覆写参数。

策略引擎：五道闸

  • 单笔金额上限
  • 日累计金额上限
  • 类目白名单
  • 商户黑名单
  • 大额人工审批阈值

核心亮点：护栏是架构隔离，不是提示词

差异化创新点 · 对应评分维度「专业贴合与创新 25 分」

亮点 1 · 覆写路径对模型不可见

常见做法是把消费规则写进 system prompt，模型可通过多轮对话、角色扮演等方式被说服放行。PayPilot 把策略引擎实现为独立模块，其覆写参数不进入模型的上下文与工具列表——模型在结构上无法触达绕过开关。护栏因此是可证明的，而非需要被信任的。

亮点 2 · 事前（pre-flight）而非事后

策略检查发生在调用支付 API 之前。不过闸不生成订单、不占用资金，从流程上消除了「先斩后奏」。

亮点 3 · 证据可引用

每个候选商品与每条策略判定都引用其所依据的字段（价格、类目、商户、命中信号数），解释不是模型自由发挥，而是绑定证据生成。

亮点 4 · 零依赖 + 完全离线可复现

  • 纯 Python 标准库，pip install 无内容，评委 `git clone` 即跑。
  • 双引擎：OpenAI 兼容 LLM（可接小米 MiMo 等）或确定性离线引擎；模型不可用时自动降级，评测不依赖任何 Key。
  • 172 条断言覆盖完整 agent 循环与进程内 PayPal mock。

亮点 5 · 工程交付完备

  • OpenAPI 3.0 规范 + Postman 集合
  • Web 界面（web.py）与 HTTP 服务（server.py）
  • render.yaml 云端部署配置
  • MIT 许可，GitHub / Gitee 双公开
